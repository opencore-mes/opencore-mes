1. About this guide

1.1 Who it is for

For IT, who installs OpenCore MES; for developers who connect OpenCore MES to other systems (ERP, a LIMS, a label printer, a data platform), for the designers who write service scripts, and for IT, who issues tokens, sets secrets and runs the nodes. It describes what OpenCore MES offers today, with the limits the code holds, and marks what is planned.

The ground rule: integration is designed, not deployed. A web service, a trigger, a schedule and the outside systems they reach are design elements, drafted in a change request, reviewed, approved by the stewards of everything they reach, and live the moment the change executes: no build, no deploy, no restart. Nothing reaches the plant around that lifecycle, and every record a service reads or writes goes through the same policies, rule pipe and audit trail as a person at a form.

1.3 Conventions

  • Code is typed as it stands. JSON designs are shown as the designer's JSON tab stores them.
  • §n refers to a section of the design document, kept by the maintainers.
  • The examples use the seed's work order and lot, and a made-up ERP at https://erp.plant.local/api. The same designs are proved end to end by app/mes/test/integration.mjs, against a fake ERP.
  • Procedures (DV-…) have a Done box per step, for a printed copy.

2. Installing OpenCore MES

OpenCore MES is plain JavaScript on Node and PostgreSQL: no build step, two runtime packages (pg, and the Anthropic SDK for the copilot). One Node process is one instance; instances share one database.

Caution. In development (and on a public demo, DEMO=1, reset every night) sign-in is a picker: a person picks who they are, so anyone who can reach that instance can act as anyone. Keep development on HOST=127.0.0.1 or a network you trust. With PROD=1 the picker is off and people sign in as 2.3 describes.

2.1 What you need

WhatVersionWhy
Node24 or laterthe server, the script runner, the tools
PostgreSQL16 or later (the pipeline runs on 16)everything that is kept: designs, records, audit, outbox, sessions

IN-01Install from npm
PurposeA running instance from the published package, with nothing to check out: to try OpenCore MES, or to run it as a plant's.
Done byIT or a developer
Before you start
  • Node 24 and PostgreSQL are installed; your user can create databases over the local socket (or DATABASE_URL names one it may).
#Do thisYou should seeDone
1Install the package.
npm install -g @opencore-mes/server
The opencore-mes command. The package holds the code only, and nothing writes to it.
2Make a plant folder, and go into it.
opencore-mes init my-plant
cd my-plant
A plant folder: .env (its settings, commented: the database, the port, sign-in, the copilot), suites/, .local/ (the event log). An existing .env is left as it is.
3Set the database in .env (DATABASE_URL, by default postgres:///opencore_mes), then make it, with the sample plant to try it:
opencore-mes db reset --yes
Cannot be undone. It makes the database named in .env again: everything in it is lost.
The database is made, its schema loaded and the seed loaded (sample people, to try it). Without --yes it refuses: a reset loses everything in the database.
4For the plant's own installation instead, an empty database and its first administrator (replace what is between < >):
opencore-mes db reset --yes --empty
opencore-mes admin <id> "<Full name>" --url https://<this site>
Cannot be undone. The first line makes the database again (everything in it is lost); the second runs once per installation: check the id and name first.
Nobody is in it but that first administrator: designer, reviewer and sign-in administrator, approver for the department that governs. A one-time link to set their password is printed (--no-password when they sign in through SSO or the directory). Setup is open: they add the plant's people and end setup. Refused once anybody is in People & departments.
5Start it, from inside the plant folder.
opencore-mes start
“listening on http://127.0.0.1:9090”, with the folder's .env, suites and event log.
6Open it and pick a person to sign in as.The navigator, the designer, the screens. For production, set PROD=1 and a way to sign in (2.2, 2.3).
opencore-mes db migrate migrates without starting; opencore-mes token <user> "<name>" and opencore-mes password <user> --url <site> are the token and password tools of 2.3 and the tutorial. To upgrade, npm install -g @opencore-mes/server@latest and restart: the server migrates at start. Suites go in the plant folder's suites/: opencore-mes suite install <name> from the suites registry, with the plant's licence token (opencore-mes suite login; the store at suites.opencoremes.com is planned), or --from <file>.tgz for a plant with no way out; every version a plant ran is kept in suites/.versions/ (suite list, suite use <name>@<version>). The contracts are packages too, with their kits: @opencore-mes/equipment-adapter and @opencore-mes/http-apis.

2.3 Sign-in

Who may sign in is People & departments' to say: a person active there, nobody else. Someone the plant's identity provider or directory knows, but People & departments does not, is refused by name and told to ask whoever keeps it. How people prove who they are is any of these, together:

WaySettingsNotes
Single sign-on (OpenID Connect)OIDC_ISSUER, OIDC_CLIENT_ID, OIDC_CLIENT_SECRETRegister https://<this site>/login/sso/callback with the provider, or set OIDC_REDIRECT_URI. The authorization code flow with PKCE; the ID token's signature, issuer, audience, expiry and nonce are checked. The sign-in id is the preferred_username claim, or OIDC_CLAIM. OIDC_LABEL names the button. Multi-factor is the provider's.
The plant's directory (LDAP, Active Directory)LDAP_URL, LDAP_USER_DNA bind as the person with the password they typed: ldaps://dc.plant:636, and {user}@plant.local (AD) or uid={user},ou=people,dc=plant,dc=example. LDAP_CA_FILE for a plant CA. ldap:// sends passwords in the clear: the server warns.
A password of OpenCore MES's ownon unless PASSWORDS=0For plants without either. IT gives a one-time link, valid 3 days unless PASSWORD_LINK_DAYS or --days says (up to 14): node app/mes/db/password.mjs olga --url https://mes.plant. The person sets it there (12 characters at least) and changes it from their name at the top right; a change signs them out elsewhere.
The pickerdevelopment, DEMO=1, or PICKER=1Anyone as anyone, no password. Never on an instance others can reach.

A person with a password here signs in with it, anyone else through the directory. Five wrong passwords in a row lock the sign-in id for 15 minutes. Sign-ins (and the way), refusals (and why), sign-outs, links and passwords set are in the audit trail under $auth. At start, the server prints the ways that are on. Planned: password ageing, SAML.

2.4 Scaling out

  • A read replica. Writes go to the primary; reads a replica can serve go to it once it has replayed every write this process committed (the replay fence), waiting at most 250 ms before the primary answers instead. Sessions, idempotency keys, the write path and the designer stay on the primary.
  • Several instances. BUS=1 on each: every change's targets reach every instance, so a save on one re-runs the open lists on all. Put a balancer in front that keeps a browser on one instance (its live stream and its calls must meet): app/mes/lb.mjs for a trial (LB_PORT, BACKENDS), HAProxy, nginx or a cloud balancer in production, with the same rule. /healthz answers 503 while an instance drains.
  • Nodes for integration. Every instance is a node: it may plan schedules and run triggers. Tag the ones inside the network that reaches ERP (NODE_TAGS=erp) and keep those services to them (5.11).

app/mes/README.md has the commands and the measurements (a replica took 8.6 times fewer commits off the primary; three instances shared 100 saves a second evenly).

3. How integration works

3.1 The two elements

ElementWhat it isHolds
ConnectionAn outside systemits base URL; its authentication (none, bearer, header, basic) naming a secret; allow, the only requests services may send it; its timeout; its stewards
ServiceA script, and what may set it offits input; whether it is a web service; its callers; its triggers (record events, schedules); who it acts as; what it may reach (objects and connections); the node tag its runs keep to; its stewards

A service is set off four ways, all running the same script the same way: an outside system calls it over HTTP; a person calls it from the designer (Try it); a record event; the clock. Whichever, it runs as the identity its design names, and reaches only what its design declares.

3.2 Data flows

Inbound ERP → POST /svc/v1/erp_work_order_in (token: user erp) → callers checked → input checked → script → ctx.records.create("work_order", …) as the service's identity → work order's policy, rule pipe, audit → { output }
Outbound a lot released (any form, transaction, service or import) → in the same database transaction, an outbox row → after the commit, a node's outbox worker → script → ctx.http("erp", …): allowed request, secret added on the server → ERP → done, or retried while ERP is down
Scheduled the clock → the scheduler plans the run once, whatever the number of nodes → outbox → script with ctx.event.previous.output (its cursor) → its next page at once if it asks for more

3.3 Identity: who a service acts as

Its design's Identity tab (runAs) says who it acts as. Whoever it is, every record it touches is checked as that identity, exactly as at a form, and the audit names on whose behalf it acted.

runAsActs asUse it when
service (the default)its own identity, service:<name>, holding exactly the object roles its design grants ("roles": { "work_order": ["planner"] }), on behalf of its caller or the eventalmost always: a service can do no more than was approved, whoever calls it; granting a role is approved by that object's stewards
callerwhoever called it, with their own rightsa service people call to do what they could do themselves; never with triggers or schedules (they have no caller)
a user id (erp)that integration user, with that user's rolesan outside system whose rights are managed as a person's

3.4 Governance: deny by default, approved by whoever answers

  • Callers. Nobody calls a service until its callers name them (users, groups). A refused caller reads who may call and which stewards decide.
  • Reach. A service touches only the objects and operations in uses.objects (read, create, update, action, archive), only the connections in uses.connections, and runs only the transactions in uses.transactions; it sends a connection only what the connection allows. Anything else is a fault: logged, refused.
  • Approval. A service answers to its own stewards and to the stewards of what it reaches: every object it may write, reacts to, or holds a role on, and every connection it uses. An ERP confirmation of lot releases is approved by whoever stewards the connection and the lot.
  • Audit. Every run, refused or not: who, how (web, UI, trigger, schedule), the input, the output, each request sent (connection, method, path, status, time; never a secret), and any refusal. Every record write inside it is audited as its identity, on behalf of the caller or the event.

5.3 The script contract

One file, one function of the service's name, context in, context out. Nothing else in the file: no import, no other statement. The new script the designer makes:

// ctx.http(connection, { method, path, query, body }) → { status, ok, body }: only what the connection allows
// ctx.transactions.run(name, input, { key }) → { run, changes, records }: a transaction it may run (uses.transactions), all or nothing

A refusal throws with the transaction's words and fields. key (at most 60 characters: the lot's number, the event's id) makes a retried run answer the first. A transaction a person signs is never run by a service. In a dry run it is planned, not run

Every record call goes through the object's policies and rule pipe as ctx.user, is audited, and seals the record. Write records only this way: one written straight in the database (an import by SQL, a fix by hand) is found by the data integrity review, with the database user it came from, and stays a finding until someone closes it with a signed non-conformance report. A refused write throws with the object's own words. About ctx.http:

  • The path is relative to the connection's base URL, starts with /, has no .., //, ?, # or backslash; parameters go in query.
  • The body is sent as JSON (not with GET); the answer is parsed when it says it is JSON. Answers over 1 MB are refused.
  • Redirects are never followed. The connection's credential is added on the server; the script never sees it.
  • An unreachable system or a timeout throws a fault that asks for a retry.

A trigger's run is claimed for 2 minutes (a node that dies mid-run leaves it to another), and retried after 2, 4, 8, … seconds (at most 5 minutes apart), up to 10 attempts; then it is dead, and the event log says so (trigger.dead). Send again on the service's Activity tab runs a retrying, dead or rejected one again.

5.5 Triggers: exactly once to enqueue, at least once to run

  • A record write that matches a trigger writes its outbox row in its own database transaction: a committed release always sets the trigger off, a rolled-back one never.
  • Every node's outbox worker claims due rows with FOR UPDATE SKIP LOCKED, ten at a time: several nodes share the work, none runs a row twice at once.
  • The service runs as its current published version, as its identity, after the event.
  • A service never sets itself off; a chain of services setting each other off stops at three.
  • Make the other side idempotent. A run may, rarely, reach it twice (a node dies after ERP answered). Send the event's id (ctx.event.id with the event kind) as the other system's key.

A run is planned once, however many nodes plan; a schedule seen for the first time is planned from then on. ctx.event.previous is the last successful run ({ at, output }), so a script keeps its cursor in its output. A run that answers output.more: true gets its next page at once (ctx.event.page), up to 100 pages. Pause, resume and Run now are operations in the monitor: audited, not design changes.

A sync by the clock: its connection allows GET /orders, and it reaches work_order with read, create and update.

// Every 15 minutes: the orders ERP changed since the last successful run, a page at a time.
export default async function erp_orders_pull(ctx) {
  const since = ctx.event.previous?.output?.cursor ?? "2026-01-01T00:00:00Z";
  const res = await ctx.http("erp", { method: "GET", path: "/orders", query: { changedSince: since } });
  if (res.status >= 500) throw Object.assign(new Error("ERP is unavailable"), { retry: true });
  if (!res.ok) throw new Error(`ERP refused the order list (${res.status})`);
  for (const order of res.body.orders) {
    const [known] = await ctx.records.list("work_order", { wo_no: order.wo_no });
    if (known) await ctx.records.update("work_order", known.id, { qty: order.qty });
    else await ctx.records.create("work_order", { wo_no: order.wo_no, item: order.item, qty: order.qty, line: order.line });
  }
  ctx.output = { cursor: res.body.until, more: res.body.hasMore === true };
  return ctx;
}

5.9 Security

  • Scripts run apart. Every rule and service script runs in the script runner: a process of its own beside each web process, started with Node's permission model (it reads only the app's files, writes none, starts no process) and an empty environment, so it holds no database address, secret or key. Jobs run in worker threads with a memory limit; one past its deadline is terminated. A script reaches records and systems only through ctx.
  • No network from a script but ctx.http, through a connection's allow list. No fetch, no Math.random: the editor warns about both.
  • Secrets are set on the server (MES_SECRET_<NAME>), never in a design, a review, the copilot's context or the audit. Changing a value is operations; changing which secret a connection uses is a design change.
  • Tokens are shown once and kept as a hash; a designer revokes an AI token in AI access.
  • Public demos and sandboxes reach no outside system: a call is refused, saying so.

The operating system's walls are each installation's to turn on. What the product does everywhere stops at Node's walls and the script's context. On Linux, add the kernel's: install bubblewrap (apt-get install bubblewrap) and, on Ubuntu 23.10 and later, its AppArmor profile (install -m 0644 ops/script-runner-sandbox.apparmor /etc/apparmor.d/opencore-mes-bwrap && apparmor_parser -r /etc/apparmor.d/opencore-mes-bwrap: those versions refuse user namespaces without one, which is also why unshare -r -n fails there); then set SCRIPT_RUNNER_WRAP=ops/script-runner-sandbox.sh. The runner then has a network namespace with loopback only, a read-only file system of the libraries, Node and the app's code, and no capabilities.

Check it by what the runner finds. At start it reports whether it sees any network and the sandbox it is in: the start log says scripts: isolated (bwrap): no network, …, and /healthz shows "scripts": {"network": "none", "sandbox": "bwrap", …}. "network": "host" means the walls are not there (a production instance also writes scripts.unisolated to its event log). Once they hold, set SCRIPT_ISOLATION=required: the instance refuses to start without them.

Caution. Until SCRIPT_RUNNER_WRAP is set, and /healthz shows "network": "none", a script that found a way out of its context would have the host's network (though no credentials). Off Linux there is no wrapper.

5.10 Testing

  • As you type: the script is parsed in the browser (never run there); syntax errors are marked on their line anywhere; calls the script will not have are warned about.
  • Dry run: executed on the server as the service will run: real reads; writes through policy and the rule pipe, not saved; requests checked and answered from responses ({ "POST /confirmations": { status, body } }), never sent. A runtime error is marked on its line.
  • Test cases (Save as test case, or written): { name, run: { input } | { event, responses }, as?, expect: { ok?, output?, error?, writes?, requests? } }. A new or changed script without one, or with a failing one, fails the fitness test, which runs them all on submit.
  • End to end: app/mes/test/integration.mjs designs, approves and calls an ERP integration against a fake ERP (wrong caller, bad input, a rule's refusal, a retry by key, a confirmation while ERP is down); app/mes/test/scheduler.mjs proves the schedules. Both run in npm run test:all.

6. Recipes

6.1 Inbound without duplicates

Have the caller send an Idempotency-Key per business message (the order number and its revision). Inside the script, guard on the natural key too, for a message sent again under another key:

const [known] = await ctx.records.list("work_order", { wo_no: ctx.input.wo_no });
if (known) { ctx.output = { id: known.id, state: known.state, existed: true }; return ctx; }

6.2 Saying no with the right field

Throw with the input it is about; a caller reads 422 with the field named, as a form does:

if (ctx.input.qty > 10000) throw Object.assign(new Error("At most 10 000 per order."), { field: "qty" });

6.3 Down is not no

Tell a system that is down (5xx, unreachable) from one that refuses (4xx). Throw with retry: true only for the first: a trigger is retried; a refusal is final, and its words are kept.

6.4 Choosing the identity

Prefer the service's own role: what it may do is on the service, approved by the stewards of each object it touches, and does not grow when someone gives the integration user another role. Use a named user when your plant manages the outside system's rights as a person's. Use the caller only for services people call to do, faster, what they may do anyway.

6.5 Keeping a run inside the right network

Give the nodes inside the network that reaches ERP a tag (NODE_TAGS=erp) and the service runOn: "erp"; the monitor warns when no live node has the tag.

7.2 Versions and notice

/ai/v1 and /svc/v1 keep what they promise for as long as /v1 runs: the contract docs/contracts/http-apis writes it down (every /ai/v1 operation with its scope and the fields it reads; the /svc/v1 envelope, its statuses and its error body { error, code?, fields? }). A new version may add; nothing promised leaves /v1 (that is /v2, beside it).

  • Every answer carries API-Version: 1.3.
  • Notice first. What /v1 will lose is marked deprecated at least 180 days before it goes; each answer to it then carries Deprecation (when it was deprecated), Sunset (the date after which it may go) and Link (its successor). Log them, and move before the sunset. Nothing is deprecated today.
  • A plant's web services are the plant's promise to you. A change that would break a caller who called in the last 30 days is refused at the plant's review unless the plant gave notice first: the service then answers you with the same headers until its sunset, and its OpenAPI description says until when and what to use instead.

Check an instance yourself, changing nothing: node docs/contracts/http-apis/kit.mjs --url <the MES> --token <a token> (add --service <name> --input <json> to try a call and its retry; --json for a program).

7.3 Excel import and export

Records go in and out as spreadsheets from Data → Import / export, through the same forms' checks, as the person importing: what an object's design allows (create, update, the key rows are matched by). See the user guide, section 13.

7.4 What is not an interface

The browser's own calls (/api/…) and the database are internals: they change without notice and are not to be built on. Integrate through web services, connections, the AI API, or files.
